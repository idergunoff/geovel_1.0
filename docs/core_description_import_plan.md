# План разработки импорта описаний керна из DOC/DOCX

## 1. Цель

Добавить в GeoVel пакетный импорт описаний керна из документов Microsoft Word. Импорт должен:

- находить существующую скважину по номеру/названию и площади;
- извлекать из таблиц интервалы глубин и исходное текстовое описание;
- извлекать и хранить указанного в документе автора описания керна;
- распознавать породы, признаки и степень нефтенасыщенности;
- позволять проверить и отредактировать результат до записи;
- сохранять только выбранные пользователем интервалы;
- полностью сохранять исходный текст и происхождение данных;
- не создавать дубли при повторной загрузке;
- допускать расширение словаря без изменения алгоритма разбора;
- обрабатывать несколько документов за один запуск.

Главный принцип: автоматизация не должна скрывать неоднозначность. Уверенные результаты можно выбирать автоматически, а спорные сопоставления скважин и распознанные признаки должны явно показываться пользователю.

## 2. Границы первой версии

В первую версию входят:

1. анализ предоставленных примеров `.doc` и `.docx`;
2. преобразование старого `.doc` в `.docx` перед разбором;
3. чтение шапки и таблиц DOCX;
4. поиск существующей скважины без автоматического создания новой;
5. извлечение верхней и нижней глубины интервала;
6. хранение полного текста описания и фамилии/подписи автора описания керна;
7. распознавание основных/вторичных пород и нефтенасыщенности правилами;
8. предварительный просмотр и ручное исправление;
9. выбор отдельных интервалов для сохранения;
10. пакетный импорт и защита от повторной загрузки;
11. миграции БД и автоматические тесты.

Не входят в первую версию:

- безусловное использование внешней LLM;
- автоматическое создание скважин по неполному совпадению;
- распознавание сканированных страниц средствами OCR;
- обучение модели классификации на небольшом наборе примеров.

Эти возможности можно добавить позднее, не меняя основную модель хранения.

## 3. Этап 1. Изучение примеров документов

До проектирования окончательных правил необходимо исследовать все предоставленные примеры Word-файлов. Оригиналы не следует добавлять в Git, если они содержат конфиденциальные данные. Для воспроизводимых тестов из них создаются обезличенные минимальные фикстуры.

### 3.1. Инвентаризация

Для каждого файла зафиксировать:

- формат: `.doc` или `.docx`;
- возможность открытия и отсутствие повреждений;
- наличие текста в абзацах, таблицах, колонтитулах и текстовых блоках;
- количество таблиц, строк и колонок;
- объединённые ячейки по горизонтали и вертикали;
- наличие повторяющейся шапки на каждой странице;
- способ записи номера скважины и площади;
- способ записи автора описания керна (обычно строка `Описал` в конце документа);
- названия и порядок колонок;
- способ записи интервала: две колонки или одно значение вида `1234,5–1238,0`;
- единицы измерения;
- пустые значения, переносы и продолжения описаний между строками;
- наличие именованных геологических границ помимо интервалов керна;
- качество и разнообразие текстовых описаний.

### 3.2. Матрица вариантов

Составить таблицу различий между документами:

| Признак | Вариант | Файлы | Решение парсера |
|---|---|---|---|
| Скважина | `Скважина № 123` | ... | правило шапки |
| Площадь | `Северная площадь` | ... | нормализация площади |
| Автор описания | `Описал геолог: Иванов И. И.` | ... | правило подписи в конце документа |
| Интервал | колонки `От`/`До` | ... | раздельный разбор |
| Интервал | `1234,5-1238,0` | ... | разбор диапазона |
| Описание | объединённая ячейка | ... | разворачивание merge |

Матрица становится основанием для правил, тестов и сообщения о неподдерживаемом формате. Неизвестную структуру нельзя молча трактовать как известную.

### 3.3. Корпус терминов

Из примеров собрать без исправления исходного текста:

- все названия пород и словоформы;
- конструкции `с прослоями`, `переслаивание`, `включения`, `обломки`, `переходящий в`;
- положительные признаки нефти;
- степени нефтенасыщенности;
- отрицания (`не нефтенасыщен`, `без признаков нефти`);
- неопределённые выражения (`возможно`, `предположительно`, `местами`);
- опечатки и принятые сокращения.

Для каждой характерной строки вручную подготовить ожидаемый структурированный результат. Этот набор станет эталонным тестовым корпусом.

### 3.4. Результат этапа

- отчёт о восьми примерах и найденных форматах;
- обезличенные DOCX-фикстуры;
- набор ожидаемых результатов в JSON;
- решение о поддержке каждого варианта;
- перечень вопросов пользователю по неоднозначным данным.

Результаты выполненного исследования находятся в
[`docs/core_description_stage1/`](core_description_stage1/report.md), а
генератор обезличенных документов и ожидания для них — в
[`tests/fixtures/core_description/`](../tests/fixtures/core_description/README.md).

## 4. Архитектура

Логику следует разделить на независимые слои:

1. **конвертация** — безопасное преобразование `.doc` в `.docx`;
2. **извлечение** — чтение абзацев и таблиц без предметной интерпретации;
3. **распознавание структуры** — шапка, колонки, строки и интервалы;
4. **семантический разбор** — породы и нефтенасыщенность;
5. **сопоставление** — поиск скважины в БД;
6. **валидация** — ошибки, предупреждения, уверенность и дубли;
7. **представление** — пакет документов и редактируемый предпросмотр;
8. **сохранение** — транзакционная запись только выбранных строк.

Парсер не должен напрямую вызывать PyQt или записывать в БД. Он возвращает типизированный промежуточный результат, пригодный для модульного тестирования.

Пример контракта:

```python
ParsedCoreDocument(
    source_path="example.docx",
    file_hash="...",
    well_name="123",
    area_name="Северная",
    intervals=[
        ParsedCoreInterval(
            top_depth=2450.0,
            bottom_depth=2453.5,
            raw_description="...",
            rocks=[...],
            oil_saturation="intense",
            confidence=0.95,
            warnings=[],
            source_table=0,
            source_row=7,
        )
    ],
)
```

## 5. Работа с DOC и DOCX

### 5.1. DOCX

DOCX читается как Open XML-пакет с помощью `python-docx`; при необходимости низкоуровневые XML-узлы используются для сохранения порядка абзацев/таблиц и корректной обработки объединённых ячеек.

Нужно учитывать:

- текст может состоять из нескольких `run`;
- переносы строк могут находиться внутри ячейки;
- вертикально объединённая ячейка не должна создавать ложные дубли;
- повторяющиеся заголовки страниц не являются интервалами;
- пустая ячейка иногда означает продолжение значения сверху.

### 5.2. Старый DOC

Бинарный `.doc` не следует разбирать как DOCX. Предлагаемый процесс:

1. проверить доступность LibreOffice в окружении;
2. конвертировать файл во временный `.docx` в headless-режиме;
3. не изменять исходный файл;
4. вычислить хеш исходного файла и хранить его как идентификатор импорта;
5. явно сообщить пользователю, если конвертер отсутствует или преобразование не удалось.

Конвертация выполняется до пакетного разбора. Ошибка одного документа не должна останавливать остальные.

## 6. Извлечение шапки

Шапка ищется не по фиксированному номеру абзаца, а по набору меток и регулярных выражений:

- `скважина`, `скв.`, `№ скв.`;
- `площадь`, `пл.`;
- значения в соседней ячейке или после двоеточия;
- варианты регистра, пробелов и `ё/е`.

Следует хранить одновременно:

- исходное значение из документа;
- нормализованное значение для поиска;
- правило, которым значение найдено;
- уверенность и предупреждения.

Если в документе найдено несколько противоречащих значений, автоматическое сопоставление запрещается.

### 6.1. Извлечение автора описания керна

Автор описания ищется во всём документе, в первую очередь после целевой таблицы и
в последних непустых абзацах, по меткам `описал`, `описал геолог` и их вариантам.
Обычно это фамилия с инициалами в конце файла. Необходимо хранить исходную строку
подписи и отдельно очищенное отображаемое имя автора. Нормализация убирает только
метку, повторяющиеся пробелы и служебные символы; фамилию, инициалы и их порядок
исправлять или дополнять нельзя.

Отсутствие автора или неоднозначная подпись не блокируют импорт интервалов, но
формируют предупреждение для предпросмотра. Автор документа не является
пользователем, выполняющим импорт: это разные поля аудита.

## 7. Сопоставление со скважиной

### 7.1. Правила

1. Нормализовать номер/название скважины и площадь.
2. Найти точные совпадения номера.
3. При нескольких совпадениях использовать площадь.
4. Нечёткое совпадение показывать как предложение, а не подтверждать автоматически.
5. При отсутствии уверенного результата потребовать ручной выбор.
6. Не создавать новую скважину автоматически из описания керна.

### 7.2. Пакетные решения

Пользователь может подтвердить соответствие один раз и применить его к документам с той же нормализованной парой «скважина + площадь». Решение действует только в текущей сессии импорта, если отдельно не реализована таблица постоянных алиасов.

### 7.3. Аудит

Для документа сохраняются:

- значения из шапки;
- выбранный `well_id`;
- способ выбора: автоматический или ручной;
- оценка совпадения;
- пользователь, если в приложении появится учёт пользователей.

## 8. Распознавание таблицы и интервалов

### 8.1. Поиск колонок

Колонки определяются по расширяемым алиасам заголовков, например:

- верх: `от`, `кровля`, `верх`, `начало интервала`;
- низ: `до`, `подошва`, `низ`, `конец интервала`;
- диапазон: `интервал`, `глубина`;
- описание: `описание`, `литологическое описание`, `описание керна`.

Если подходящих таблиц несколько, рассчитывается оценка структуры. Неоднозначный выбор должен отображаться пользователю.

### 8.2. Числа и диапазоны

Поддержать:

- десятичную точку и запятую;
- пробелы и неразрывные пробелы;
- суффикс `м`;
- дефис, короткое и длинное тире;
- раздельные колонки и единую строку диапазона.

Валидация:

- глубины конечны;
- `top_depth < bottom_depth`;
- интервал не нулевой;
- подозрительно большая мощность выдаёт предупреждение;
- пропуск одной границы не угадывается без подтверждённого правила;
- пересечения соседних интервалов отображаются пользователю.

### 8.3. Именованные границы

Интервалы керна хранятся в новой таблице и не превращаются в записи `Boundary`. Именованная геологическая граница может дополнительно записываться в `Boundary` только после того, как примеры подтвердят её семантику и пользователь выберет такую опцию.

## 9. Расширяемый словарь

### 9.1. Формат первой версии

Первую версию словаря хранить в версионируемом JSON-файле. Алгоритм и данные словаря разделяются. Каждое правило содержит:

```json
{
  "id": "oil_saturation.intense.01",
  "category": "oil_saturation",
  "canonical_value": "intense",
  "patterns": ["интенсивно нефтенасыщенный"],
  "pattern_type": "phrase",
  "priority": 100,
  "enabled": true,
  "comment": "Явное указание интенсивной нефтенасыщенности"
}
```

Допустимые типы правил:

- точное слово;
- фраза;
- безопасное регулярное выражение;
- отрицание;
- контекстное отношение.

### 9.2. Категории

- `rock` — канонические породы и словоформы;
- `rock_relation` — основная порода, прослой, включение, переслаивание;
- `oil_indicator` — признаки нефти;
- `oil_saturation` — слабая, средняя, интенсивная, неизвестная;
- `negation` — отсутствие признака;
- `uncertainty` — возможно, предположительно, местами;
- `ignore` — служебные обороты.

### 9.3. Управление изменениями

- файл проходит проверку схемы при запуске;
- неизвестная категория или повторяющийся `id` являются ошибкой конфигурации;
- словарь имеет версию;
- документ хранит версию парсера и словаря;
- тесты фиксируют поведение каждого правила;
- в следующей версии можно добавить редактор словаря или перенести правила в БД с импортом/экспортом JSON.

### 9.4. Объяснимость

Результат содержит список сработавших правил, фрагмент текста и позицию совпадения. Пользователь должен видеть, почему выбраны конкретная порода и степень насыщенности.

## 10. Семантический разбор описания

### 10.1. Нормализация

- регистр и `ё/е`;
- типы пробелов и тире;
- переносы строк;
- пунктуация для поиска без изменения `raw_description`.

### 10.2. Породы

Для каждого упоминания определяются:

- каноническое название;
- исходная словоформа;
- роль: `primary`, `interlayer`, `inclusion`, `alternation`, `unknown`;
- положение в тексте;
- уверенность.

### 10.3. Нефтенасыщенность

Минимальная шкала:

- `none` — явно отсутствует;
- `weak` — слабая;
- `medium` — средняя/умеренная;
- `intense` — интенсивная;
- `present` — есть признак без степени;
- `uncertain` — предположительная или противоречивая;
- `unknown` — сведений нет.

Отрицание имеет приоритет только в своей смысловой области. Фраза «аргиллит не нефтенасыщен, прослои песчаника интенсивно нефтенасыщенные» не должна терять насыщенность песчаника.

### 10.4. Связь признака с породой

Правила учитывают предложение/часть предложения, ближайшее упоминание породы и конструкции отношений. Помимо общей оценки интервала хранится насыщенность отдельных упоминаний пород. Противоречивый результат помечается `needs_review`.

### 10.5. Уверенность

Оценка формируется из отдельных факторов:

- надёжность структуры таблицы;
- корректность глубин;
- точность словарного совпадения;
- наличие отрицаний/неопределённости;
- однозначность связи характеристики с породой.

Порог автопредварительного выбора должен быть настройкой, а не константой интерфейса.

## 11. Модель данных

Окончательные названия уточняются после изучения примеров, но базовая схема следующая.

### 11.1. `CoreDescriptionDocument`

- `id`;
- `well_id`;
- `source_file_name`;
- `source_file_hash` (SHA-256 исходного файла);
- `source_format`;
- `well_name_raw`;
- `area_name_raw`;
- `described_by_raw` — исходная строка подписи автора описания керна;
- `described_by` — очищенные фамилия и инициалы для отображения и поиска;
- `parser_version`;
- `dictionary_version`;
- `match_method`;
- `match_confidence`;
- `imported_at`;
- `status`;
- диагностический JSON без содержимого самого бинарного файла.

### 11.2. `CoreDescriptionInterval`

- `id`;
- `document_id`;
- `well_id` для удобства запросов и контроля целостности;
- `top_depth`;
- `bottom_depth`;
- `raw_description`;
- `normalized_description`;
- `oil_saturation`;
- `confidence`;
- `needs_review`;
- `source_table_index`;
- `source_row_index`;
- `manually_edited`;
- `recognition_details` в JSON.

### 11.3. `CoreDescriptionRock`

- `id`;
- `interval_id`;
- `rock_name`;
- `role`;
- `oil_saturation`;
- `source_text`;
- `confidence`;
- позиции совпадения в нормализованном тексте.

### 11.4. Ограничения и индексы

- внешние ключи и каскадное удаление дочерних записей;
- индекс по `well_id`, `top_depth`, `bottom_depth`;
- уникальность документа по хешу с явно определённым режимом повторного импорта;
- `top_depth < bottom_depth` проверяется сервисом и, если поддерживается СУБД, ограничением БД;
- удаление/замена ранее импортированного документа выполняется явно.

Миграция должна поддерживать SQLite и фактическую промышленную СУБД проекта.

## 12. Защита от дублей и повторный импорт

Перед разбором рассчитывается SHA-256. Возможные состояния:

- новый файл;
- уже полностью импортированный файл;
- тот же документ с другим именем;
- изменённая версия похожего документа;
- интервалы пересекаются с данными другого документа.

При точном совпадении хеша пользователь выбирает:

- открыть существующий результат;
- пропустить файл;
- заменить ранее выбранные интервалы после подтверждения.

Повторное молчаливое добавление запрещено. Для приблизительных дублей показываются совпадающие глубины и тексты, но решение остаётся за пользователем.

## 13. Пакетный импорт

### 13.1. Выбор источников

- один файл;
- несколько файлов;
- каталог с опциональным обходом подкаталогов;
- фильтр `.doc`/`.docx`;
- стабильный порядок обработки.

### 13.2. Этапы пакетной задачи

1. инвентаризация и вычисление хешей;
2. конвертация `.doc`;
3. извлечение структуры;
4. разбор содержимого;
5. сопоставление скважин;
6. подготовка общего предпросмотра;
7. выбор документов и интервалов;
8. сохранение по одному документу;
9. итоговый отчёт.

### 13.3. Изоляция ошибок

Ошибка файла фиксируется рядом с ним и не останавливает пакет. Сохранение каждого документа выполняется отдельной транзакцией. В конце показываются количества:

- обработано;
- успешно сохранено;
- пропущено пользователем;
- обнаружено повторно;
- требует проверки;
- завершилось ошибкой.

Парсинг больших пакетов выполняется вне GUI-потока с безопасной передачей прогресса в PyQt. Отмена прекращает новые работы, но не оставляет частично записанную транзакцию.

## 14. Интерфейс предварительного просмотра

Режим импорта открывается кнопкой **«Керн»** с именем `core_description`,
расположенной во вкладке **`layer, well`**. Эта кнопка является основной точкой
входа как для загрузки одного документа, так и для пакетного импорта. Отдельный
пункт меню в первой версии не требуется.

### 14.1. Список документов

Колонки:

- флажок импорта;
- имя файла;
- скважина и площадь из документа;
- автор описания керна из документа;
- выбранная скважина БД;
- статус совпадения;
- число найденных/выбранных интервалов;
- предупреждения и ошибки.

### 14.2. Интервалы выбранного документа

Колонки:

- флажок сохранения;
- верх и низ;
- основная порода;
- дополнительные породы/отношения;
- нефтенасыщенность;
- уверенность;
- полный исходный текст;
- состояние проверки.

Действия:

- выбрать/снять все;
- выбрать уверенные;
- выбрать нефтенасыщенные;
- фильтровать по глубине, породе, насыщенности и состоянию;
- редактировать распознанные значения;
- вернуть автоматическое значение;
- просмотреть сработавшие правила;
- перейти к следующей проблемной строке.

Фильтрация не должна изменять выбор скрытых строк. Перед сохранением показывается точное число документов и интервалов.

### 14.3. Правила начального выбора

По умолчанию можно отметить корректные интервалы уверенно сопоставленной скважины. Строки с ошибочными глубинами, невыбранной скважиной, конфликтом или низкой уверенностью не отмечаются автоматически. Пользователь всегда может изменить выбор.

## 15. Сервис сохранения

Сервис получает уже подтверждённую команду без зависимости от виджетов:

```python
save_core_import(
    session,
    parsed_document,
    well_id=selected_well_id,
    selected_interval_ids={...},
    edits={...},
    duplicate_policy="reject",
)
```

Он повторно валидирует данные, создаёт документ, сохраняет только выбранные интервалы и их породы, затем делает `commit`. При исключении выполняется `rollback`. Результат содержит счётчики и диагностические сообщения.

## 16. Тестирование

### 16.1. Модульные тесты

- нормализация шапки и площади;
- извлечение автора из вариантов `Описал`/`Описал геолог`, а также пустой и неоднозначной подписи;
- числа и интервалы с разными разделителями;
- поиск колонок;
- объединённые и пустые ячейки;
- словоформы пород;
- отношения пород;
- интенсивность нефтенасыщенности;
- отрицания и неопределённость;
- связь характеристики с конкретной породой;
- расчёт уверенности;
- загрузка и проверка словаря.

### 16.2. Контрактные тесты документов

Для каждого обезличенного примера проверять:

- шапку;
- исходную подпись и очищенное имя автора описания;
- выбранную таблицу;
- количество интервалов;
- точные глубины;
- полный исходный текст;
- ожидаемые структурированные признаки;
- предупреждения.

### 16.3. Тесты БД

- миграция вверх/вниз;
- связи и каскады;
- выборочное сохранение;
- rollback при ошибке;
- точные и приблизительные дубли;
- повторный импорт;
- сохранение исходной подписи и очищенного имени автора описания;
- хранение версий парсера/словаря.

### 16.4. Тесты интерфейса

- выбор файлов и каталога;
- ручное сопоставление скважины;
- открытие режима кнопкой `Керн` (`core_description`) во вкладке `layer, well`;
- отображение автора описания и предупреждения при пустой/неоднозначной подписи;
- сохранение только отмеченных строк;
- фильтры без потери выбора;
- редактирование результата;
- отмена пакетной задачи;
- отчёт о частично успешном пакете.

### 16.5. Регрессия

Запустить полный набор тестов проекта и проверить, что новая миграция не меняет существующий импорт скважин и границ.

## 17. Логирование, безопасность и конфиденциальность

- не выводить полные описания керна в обычный лог;
- логировать имя файла, номер строки, код ошибки и технический контекст;
- не выполнять макросы и вложения Word;
- ограничить допустимые расширения и размер файла;
- распаковывать DOCX с защитой от zip bomb и обхода путей;
- временные файлы DOC-конвертации удалять после обработки;
- внешние сетевые сервисы не использовать без отдельного согласования;
- оригинальный бинарный документ не хранить в БД по умолчанию.

## 18. Наблюдаемость и отчёт

Для каждого документа формируется диагностическая запись:

- длительность конвертации и разбора;
- выбранный распознаватель формата;
- найденные поля шапки;
- найденный автор описания керна;
- число прочитанных, корректных, выбранных и сохранённых интервалов;
- ошибки и предупреждения по строкам;
- версии парсера и словаря.

Пользователь может сохранить итог пакетного импорта в CSV/JSON без полного конфиденциального текста.

## 19. Возможное развитие

После накопления исправленных пользователем примеров:

- редактор словаря в интерфейсе;
- постоянные алиасы площадей и скважин;
- сравнение версий одного документа;
- повторный семантический разбор уже сохранённого исходного текста;
- локальная NLP/LLM-модель только для строк с низкой уверенностью;
- OCR для сканированных документов;
- визуализация интервалов на планшете скважины.

Любая модель машинного обучения должна возвращать структурированный результат с уверенностью и не заменять предпросмотр.

## 20. Этапы реализации и контрольные точки

Ниже приведён сводный порядок этапов. Подробные требования к этапу 1 описаны в разделе 3; требования к архитектуре, данным, интерфейсу и тестированию из предыдущих разделов распределяются между этапами 2–7.

### Этап 1. Исследование примеров документов

- изучить все примеры;
- подготовить матрицу форматов и эталонный корпус;
- согласовать трактовку глубин, границ и нефтенасыщенности.

**Готово, когда:** для каждого примера известен ожидаемый результат и список неподдерживаемых случаев.

### Этап 2. Разработка чистого парсера

- реализовать модели промежуточных данных;
- DOC-конвертацию;
- извлечение DOCX;
- шапку, таблицу и интервалы;
- подпись автора описания керна в конце документа;
- CLI/тестовый вывод JSON.

**Готово, когда:** все поддержанные обезличенные примеры разбираются без БД и GUI.

Реализация и инструкция по запуску: [`core_description_parser.md`](core_description_parser.md).

### Этап 3. Разработка словаря и семантического разбора

- создать схему и начальный словарь;
- распознавать породы, отношения и нефтенасыщенность;
- добавить объяснения и уверенность.

**Готово, когда:** эталонный корпус проходит тесты, а спорные строки корректно помечаются.

### Этап 4. Разработка модели и сервисов базы данных

- согласовать схему;
- добавить модели и Alembic-миграцию;
- реализовать сопоставление, дубли и сервис сохранения.

**Готово, когда:** тесты подтверждают выборочное и идемпотентное сохранение.

### Этап 5. Разработка предпросмотра одного документа

- подключение режима к кнопке `Керн` (`core_description`) во вкладке `layer, well`;
- выбор файла;
- выбор скважины;
- таблица интервалов, фильтры, редактирование и сохранение.

**Готово, когда:** пользователь может исправить результат и сохранить только отмеченные интервалы.

### Этап 6. Разработка пакетного импорта

- несколько файлов/каталог;
- фоновая обработка, прогресс и отмена;
- изоляция ошибок;
- общий отчёт.

**Готово, когда:** смешанный пакет успешно обрабатывается, а ошибочный файл не влияет на остальные.

### Этап 7. Приёмочное тестирование и документация

- полный регрессионный прогон;
- ручная проверка на оригиналах;
- проверка производительности;
- инструкция пользователя и администратора словаря.

## 21. Вопросы, которые нужно закрыть по примерам

1. Все ли глубины являются измеренной глубиной, а не абсолютной отметкой?
2. Есть ли в документах именованные геологические границы, которые нужно добавлять в `Boundary`?
3. Как трактовать пустую границу: ошибка или продолжение соседней строки?
4. Нужна ли запись интервалов без нефтенасыщенности?
5. Какое итоговое перечисление степеней нефтенасыщенности требуется предметной области?
6. Может ли один документ содержать несколько скважин?
7. Может ли один интервал быть продолжен в следующей таблице/странице?
8. Нужно ли сохранять оригинальный DOC/DOCX вне базы для аудита?
9. Кто имеет право изменять общий словарь?
10. Как поступать, если выбранный интервал уже существует из другого источника?

## 22. Критерии приёмки первой версии

Первая версия считается готовой, если:

- все согласованные варианты примеров корректно читаются;
- скважина уверенно находится или запрашивается ручной выбор;
- глубины и полный исходный текст не теряются;
- породы и нефтенасыщенность имеют объяснимый результат;
- пользователь выбирает документы и отдельные интервалы;
- ручные исправления сохраняются;
- словарь расширяется данными без правки алгоритма;
- повторный файл не создаёт молчаливые дубли;
- пакет продолжает работу после ошибки одного файла;
- данные записываются транзакционно;
- модульные, интеграционные и регрессионные тесты проходят;
- пользовательская документация описывает импорт, предупреждения и изменение словаря.
