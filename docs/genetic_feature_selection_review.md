# Аудит подбора маски признаков и план ускорения

## Краткий вывод

Главная стоимость текущего поиска — не сам генетический алгоритм, а повторное
обучение модели для каждой маски на каждом фолде `LeaveOneGroupOut`. При размере
популяции `P`, числе поколений `G` и числе объектов `K` верхняя оценка составляет
примерно `P * (G + 1) * K` обучений модели. Например, `P=50`, `G=100`, `K=20` —
около 101 000 обучений, не считая повторно встретившихся масок.

Рекомендуемый путь: сначала убрать лишнюю работу внутри целевой функции и
добавить кэш точных масок, затем внедрить двухступенчатую оценку кандидатов и
early stopping. Параллелизм стоит добавлять только после этого и только на одном
уровне. Для большинства практических задач хорошая альтернатива полному GA —
фильтр признаков + последовательный floating search либо регуляризованная
модель; GA/NSGA-II тогда используется лишь для доработки короткого списка.

## Как поиск устроен сейчас

В проекте фактически существуют две почти одинаковые реализации:

- классификация в `classification_func.py`;
- регрессия в `regression.py`.

Последовательность обеих реализаций:

1. Из `prof_well_index` для каждой строки отдельным запросом к БД определяется
   название объекта, которое затем используется как группа.
2. Каждый признак кодируется отдельной бинарной переменной Platypus.
3. В режиме без Pareto запускается `GeneticAlgorithm`, в режимах Pareto —
   `NSGAII`. Первая цель максимизирует средний `Pipeline.score`, вторая
   минимизирует или максимизирует число включённых признаков.
4. Каждая маска проверяется полным `LeaveOneGroupOut`: pipeline заново обучается
   на каждом допустимом фолде.
5. Алгоритм выполняется синхронно по одному поколению. Через заданный интервал
   сохраняются популяция, objective values, `nfe` и состояние генератора
   случайных чисел. Сохранённую популяцию можно загрузить и продолжить поиск.
6. В интерфейсе доступны размер популяции, число поколений, период checkpoint и
   выбор направления Pareto; найденную маску можно сохранить.

Уже имеется отдельный экран классического feature selection с
`VarianceThreshold`, `SelectKBest`, correlation filter, forward/backward
selection, LASSO, Random Forest importance и Boruta. Сейчас эти методы не
связаны с GA в единый каскад.

## Обнаруженные узкие места

### 1. Повторная подготовка неизменяемых данных — высокий приоритет

В каждой оценке маски заново выполняются:

- преобразование `DataFrame` в списки, затем в `numpy`;
- выпрямление `markup` и `groups`;
- построение всех LOGO-разбиений;
- для классификации — повторный `build_pipeline`;
- для регрессии — повторное чтение UI, создание scaler/PCA/model и pipeline.

Всё это неизменно на протяжении запуска. До старта GA следует один раз получить
непрерывный `X = training_sample.to_numpy()`, одномерные `y` и `groups`, один раз
сформировать и отфильтровать список `(train_idx, test_idx)`, а estimator создавать
через `sklearn.base.clone(base_pipeline)` непосредственно перед обучением.

### 2. Нет кэша уже оценённых масок — высокий приоритет

Кроссовер, мутация, элитизм и возобновление могут породить одну и ту же маску
много раз. Сейчас каждое появление оплачивает полный LOGO. Нужен кэш
`tuple(bool mask) -> (mean_score, feature_count, fold_scores)`. Для
детерминированных estimator это точное переиспользование без изменения качества.
Для стохастических моделей следует зафиксировать `random_state`; если нужен
повторный статистический прогон, seed должен входить в ключ.

Кэш стоит сохранять в checkpoint вместе с версией схемы, fingerprint набора
данных, признаков, групп, pipeline и настроек CV. Нельзя переиспользовать его при
несовпадении fingerprint.

### 3. N+1-запросы к БД при построении групп — средний приоритет

`get_obj_title` вызывается через `Series.apply` и делает SQL-запрос для каждой
строки. Следует одним запросом получить отображение `profile_id -> object_id`
(лучше стабильный числовой id, а не потенциально неуникальный title), после чего
применить локальный `map`. Это ускорит подготовку и сделает группировку надёжнее.

### 4. Работа с UI и консолью находится в горячем цикле — средний приоритет

Для каждого фолда меняется progress bar, а для каждой маски выполняется `print`.
Это создаёт лишние события UI и особенно мешает будущему multiprocessing.
Обновлять UI достаточно один раз после evaluation batch или поколения, а
диагностику направлять в logger с настраиваемым уровнем.

### 5. Полный LOGO используется с первой до последней оценки — высокий приоритет

Большинство ранних кандидатов заведомо слабые, но получают ту же дорогую оценку,
что финалисты. Безопасная схема successive halving:

1. оценить все новые маски на фиксированных 2–3 репрезентативных группах;
2. оставить верхние 25–40%;
3. оценить их на 50% групп;
4. полный LOGO выполнять для элиты и итогового Pareto-фронта.

Группы на каждом уровне должны быть фиксированы на весь запуск, а финальное
ранжирование — основываться только на одинаковом полном наборе фолдов. Иначе
оценки кандидатов становятся несопоставимыми.

### 6. Нет критерия остановки — высокий приоритет

Цикл всегда выполняет заказанное число поколений. Следует завершать его, если
`best_score` (для GA) или hypervolume Pareto-фронта (для NSGA-II) не улучшился на
`min_delta` за `patience` поколений. Практичные стартовые значения:
`patience=10`, `min_delta=0.001`; предел числа evaluations остаётся жёсткой
страховкой.

### 7. Дублирование классификации и регрессии — архитектурный приоритет

Код checkpoint, восстановления, создания бинарной задачи, цикла поколений и
отрисовки почти одинаков. Общий сервис `FeatureMaskOptimizer` позволит один раз
реализовать cache, batching, telemetry и остановку, а из экранов передавать
подготовленные `X/y/groups`, pipeline и scoring policy. Это снижает риск, что
ускорение или исправление попадёт только в один режим.

## Замечания по корректности, которые нужно исправить до оптимизации

1. **Пустая маска возвращает две цели всегда.** В одноцелевой задаче функция
   должна возвращать один элемент, например `[worst_score]`; иначе контракт
   `Problem(..., nobjs=1)` нарушен.
2. **Пустой набор допустимых фолдов приводит к `mean([]) = NaN`.** Это возможно
   при фильтре `cov_percent`. Такую маску нужно помечать конечным худшим score и
   явно логировать отсутствие фолдов.
3. **В регрессии комментарий называет первую цель accuracy.** Фактически
   `Pipeline.score` обычно возвращает R² и может быть отрицательным. Худший score
   пустой/невалидной маски должен быть `-inf` либо заранее выбранное конечное
   нижнее ограничение, а не `0`, иначе невалидная маска может победить слабую
   модель.
4. **Направление Pareto `MAX` для числа признаков противоречит отбору.** Оно
   полезно только как диагностический режим. Для компактной маски по умолчанию
   должно быть `MIN`, либо использоваться цель
   `score - lambda * feature_fraction`.
5. **Воспроизводимость checkpoint не гарантирована.** По умолчанию при загрузке
   сохранённый RNG не восстанавливается, а вызывается `random.seed()`. Нужен явный
   пользовательский seed и восстановление состояния; seed и версии зависимостей
   следует записывать в metadata.
6. **Оценка одной маски не измеряет стабильность.** Вместе со средним нужно
   хранить standard deviation/standard error по группам. Финалисты с близким
   средним score должны сравниваться по устойчивости и числу признаков.

## Рекомендуемый план внедрения

### Этап 0 — измеримый baseline и исправления (1–2 дня)

- вынести objective evaluator в тестируемый модуль;
- исправить пустую маску, пустые folds и воспроизводимость;
- записывать `elapsed`, число model fits, cache hits, уникальные маски, score,
  число признаков и seed;
- зафиксировать 3 набора: маленький, типичный и большой, отдельно для
  классификации и регрессии.

Критерий приёмки: одинаковая маска при одинаковом seed и отсутствие `NaN`/
несоответствия числа objectives.

### Этап 1 — безопасные ускорения (2–4 дня)

1. Один раз материализовать `X/y/groups/folds`.
2. Убрать SQL, создание pipeline и обновления UI из внутренних циклов.
3. Добавить точный memoization cache с fingerprint.
4. Добавить early stopping.
5. Инициализировать часть популяции осмысленными кандидатами: all-features,
   top-k по mutual information/F-test и масками, полученными RF/LASSO/Boruta.

Ожидаемый выигрыш следует считать экспериментально. Основной показатель —
`model_fits`, поскольку wall-clock зависит от выбранной модели. Cache особенно
эффективен на поздних поколениях, а подготовка вне objective помогает при быстрых
моделях.

### Этап 2 — многоуровневая оценка (3–5 дней)

- successive halving по числу групп;
- полный LOGO только для текущей элиты и финального фронта;
- опциональный surrogate: дешёвая модель прогнозирует перспективность маски, но
  никогда не выдаёт финальный score;
- сравнить результат с baseline по полному LOGO.

Критерий: медианное время ниже минимум на 30%, а лучший подтверждённый full-LOGO
score не хуже baseline более чем на заранее согласованный допуск (например,
0.5 процентного пункта accuracy или 0.01 R²).

### Этап 3 — контролируемый параллелизм (2–4 дня)

Параллелить лучше независимые маски, а не одновременно маски, folds и внутренние
потоки модели. Иначе возникает oversubscription. Worker не должен обращаться к
Qt или общей SQLAlchemy session. В worker передаются только numpy-массивы,
индексы folds, сериализуемый estimator и mask; UI получает агрегированный прогресс
через очередь. Для тяжёлых numpy/sklearn моделей начать с
`workers=min(physical_cores, 4)` и ограничить BLAS/OpenMP одним потоком на worker.

## Альтернативы генетическому поиску

| Метод | Когда применять | Плюсы | Ограничения |
|---|---|---|---|
| Filter + SFFS/SBFS | До ~100–300 признаков, требуется понятная маска | Обычно намного меньше evaluations; floating-шаг исправляет часть ошибок greedy | Может пропустить сложное взаимодействие признаков |
| L1/Elastic Net | Линейная/почти линейная структура, много признаков | Очень быстро, встроенный контроль разреженности | Требует scaling; коррелированные признаки выбираются нестабильно |
| RF/ExtraTrees + permutation importance | Нелинейности и взаимодействия | Быстрый shortlist, уже близок текущему стеку | Impurity importance смещён; окончательно проверять permutation importance на held-out groups |
| Boruta | Нужно найти все релевантные признаки | Уже реализован, устойчивее простого top-k | Может быть дорогим и давать широкую маску |
| RFE/RFECV с group-aware CV | Умеренное число признаков | Простая интерпретация пути исключения | Обычный RFECV нужно явно настроить на group splits; иначе leakage |
| Optuna/TPE по `k` и ranking | Есть качественный ranking признаков | Поиск по `k` вместо `2^d`, удобные pruning/бюджеты | Не ищет произвольные комбинации без расширения пространства |
| Stability selection | Важна воспроизводимость признаков | Даёт частоту выбора и контроль нестабильности | Требует повторных subsample-прогонов |
| Sequential halving / Hyperband | Различается бюджет оценки кандидатов | Отбрасывает слабые маски рано | Нужна единая полная переоценка финалистов |

### Предпочтительный гибрид

1. Удалить константные и почти дублирующиеся признаки только на training data.
2. Построить объединённый ranking по mutual information/F-test и permutation
   importance, вычисленным с group-aware validation.
3. Оставить 30–80 признаков (порог проверить на данных).
4. Получить несколько масок через SFFS либо проверить top-k для сетки `k`.
5. Инициализировать ими NSGA-II и дать небольшой бюджет на поиск взаимодействий.
6. Переоценить весь итоговый Pareto-фронт полным LOGO; выбор конкретной маски
   выполнять на отдельной внешней группе или nested group CV.

Такой каскад сохраняет способность GA находить нелинейные комбинации, но резко
сокращает размерность и число дорогих обучений.

## Протокол сравнения вариантов

Для каждого метода и набора данных выполнить не менее 5 запусков с одинаковым
набором seed и одинаковыми внешними group splits. Сохранять:

- wall-clock и CPU time;
- число уникальных масок, cache hit rate и число `fit`;
- лучший full-LOGO score, разброс по группам и размер маски;
- Jaccard similarity выбранных масок между seed;
- peak RSS;
- кривую best score / Pareto hypervolume от времени и числа `fit`.

Отбор признаков должен происходить **внутри training-части внешнего split**.
Иначе сравнение вариантов будет оптимистичным из-за leakage. Для быстрой
инженерной итерации допустим фиксированный validation-набор групп, но итоговое
качество релиза следует подтверждать nested group CV или полностью отложенными
объектами.

## Практическая конфигурация первого эксперимента

- предварительный shortlist: 50 признаков;
- популяция: `max(20, 2 * shortlist_size)`, но не более 100;
- 20 поколений с `patience=7`, затем увеличить бюджет только если фронт ещё
  улучшается;
- мутация около `1 / n_features`, как сейчас;
- Pareto: максимизировать score и минимизировать число признаков;
- coarse budget: 3 фиксированные группы, full budget: все группы;
- полный LOGO для top-10 одноцелевых масок либо всего недоминируемого фронта;
- фиксированный seed, cache и checkpoint metadata.

Это не универсальные оптимальные значения, а безопасная отправная точка. Их
нужно выбирать по кривым «качество–время», а не только по максимальному score.
