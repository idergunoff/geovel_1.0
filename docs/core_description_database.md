# Модель БД и сервисы импорта описаний керна (этап 4)

Этап добавляет таблицы `core_description_document`, `core_description_interval` и
`core_description_rock`. Исходный Word-файл в БД не записывается: документ хранит
SHA-256, имя и формат источника, исходные поля шапки и подписи, версии парсера и
словаря, способ сопоставления со скважиной и диагностический JSON. Интервалы и
распознанные породы удаляются каскадно вместе с документом.

Миграция `1e2f3a4b5c6d` объединяет две существовавшие ветви Alembic и поддерживает
`upgrade`/`downgrade`. Ограничение БД и повторная проверка в сервисе требуют
`top_depth < bottom_depth`; уникальный SHA-256 не допускает молчаливого повторного
импорта.

Миграция `2f3a4b5c6d7e` добавляет к интервалам поля `thickness` (мощность, м)
и `geological_index_raw` (геологический индекс). Для существующей БД перед
запуском обновлённой программы выполните `alembic upgrade head` из каталога
проекта с настройками нужной базы. Старые интервалы сохраняются; новые поля
в них остаются пустыми. Сервис сохраняет значения из документа либо ручные
правки предпросмотра, проверяя, что мощность конечна и неотрицательна.

## Сопоставление и проверка дублей

Функция `core_description.database.match_well(session, well_name, area_name, document=parsed_document)`:

1. нормализует регистр, `ё/е`, Unicode, пробелы и служебную пунктуацию;
2. для предпросмотра с `document` автоматически выбирает скважину с точным номером
   и наибольшим числом совпавших признаков (минимум два), при равенстве — первую по id;
3. при одинаковых номерах уточняет результат по значениям `WellOptionally`
   (**Data of Well**): `Площадь`, `пл.`, `area`, `Залежь`, `Месторождение` и другим
   категориям; название площади ищется в значениях независимо от категории;
4. учитывает грамматические варианты названий («Сарабикуловское поднятие» /
   «Сарабикуловский») и номер объекта («Нефтеперспективный объект №58» /
   «Объект 58» / «58»); для названий использует сходство строго выше 50%,
   для номеров объектов — точное совпадение;
5. нечёткие совпадения возвращает только как предложения для ручного выбора,
   отдавая приоритет подходящей площади перед ограничением в десять вариантов.

При передаче `document` дополнительно сравниваются нормализованные даты начала
и окончания бурения и альтитуда устья. Даты берутся из соответствующих категорий
`WellOptionally`, альтитуда — также из `Well.alt`. Номер входит в число пяти
сравниваемых признаков наряду с площадью/участком, началом бурения, окончанием
бурения и альтитудой устья. Для автоматического выбора нужны минимум два совпадения
из пяти, включая точный номер, и хотя бы одно совпадение по альтитуде либо полной
дате начала или окончания бурения. Номер и площадь без такого подтверждения
не приводят к автоматическому выбору, даже при точном совпадении площади.
Пробелы и регистр в номере не различаются: `10 Вр`, `10вр` и `10 ВР` совпадают.
Без точного номера автоматический выбор не выполняется. Метод — `exact_name_identity`.
Каждый признак учитывается один раз независимо от количества его записей в БД.
Остальные признаки могут различаться. При нескольких записях с тем же номером
выбирается запись с наибольшим числом совпавших признаков (минимум два).
При равном максимальном числе совпадений выбирается первая по id запись.
Менее двух совпадений требуют ручного выбора. Например, три совпадения имеют
приоритет перед двумя, два — перед одним.
Приоритет и разрешение равенства по id применяются только к записям, у которых
есть подтверждение по дате бурения или альтитуде.
При повторном сопоставлении пустой сохранённый выбор не блокирует автоматический
результат; ранее выбранная вручную скважина сохраняет приоритет.
Совпадение месяца без дня отмечается как
частичное и не учитывается в счётчике; допуск для альтитуды — 2 м включительно.
Отсутствующие значения не считаются совпадениями.
Если номер залежи указан только с одной стороны, ненумерованное название площади
сравнивается с основой названия залежи: «Верхнее поднятие» соответствует «Верхнее 3».
Если номера есть с обеих сторон и различаются, совпадения нет: «Верхнее 3» и
«Верхнее 4» различаются. Для обозначений «Объект …» сохраняется точное сравнение.
Значения категорий бурения и альтитуды не используются как названия площадей.
В строке сравнения площади показывается только одна запись выбранной скважины:
категория и значение с наибольшим сходством с площадью документа. Процент и
статус относятся к этой же записи. При одинаковом сходстве выбирается первая
по id запись; при отсутствии площади в документе показывается первая площадь
скважины со статусом отсутствия данных для сравнения.
В строках дат бурения и альтитуды ячейка также содержит одно значение: для дат
предпочтение отдаётся точной дате, затем совместимой неполной дате; для альтитуды
выбирается ближайшее к значению документа число, включая `Well.alt`. При отсутствии
подходящего значения показывается первое корректное значение, а если корректных
нет — первая исходная запись. Все исходные значения доступны в подсказке ячейки
и в `database_values` результата сравнения. Статус по-прежнему учитывает все
записи: выбор одного значения для отображения не скрывает противоречий и не
превращает конфликт в совпадение.

В `diagnostics` документа сохраняются исходные и нормализованные сведения
`well_identity`, результат сравнения `well_comparison` с процентом сходства
площади и применённые пороги `well_match_policy`. Новые столбцы и миграция БД
не требуются.
В политике сохраняются `total_categories: 5` и `well_number_included: true`,
чтобы отличать новый подсчёт от прежних импортов с четырьмя признаками.
Обязательное дополнительное подтверждение записывается в `required_one_of`:
`drilling_start`, `drilling_end` или `wellhead_elevation`. Неполные даты,
некорректные значения и противоречивые данные не считаются таким подтверждением.

Площади загружаются для точных совпадений по имени либо для нечётких предложений.
Если площадь не указана, загружаются только десять лучших нечётких предложений;
если указана, площадь учитывается до ограничения списка. Идентификаторы разбиваются на пакеты по 500,
чтобы не превышать лимит SQL-параметров SQLite даже при большом числе
скважин с одинаковым именем. Это ограничение относится к сопоставлению
с базой и не зависит от исходного формата документа (`.doc` или `.docx`).

Предпросмотр использует `load_well_catalog(session)`: два запроса выбирают только
`well.id/name/alt` и `well_optionally.well_id/option/value`, без создания ORM-объектов.
Все атрибуты читаются одним проходом вместо повторных запросов с `IN` по 500 id.
Снимок передаётся в `match_well(..., document=..., catalog=...)` и используется
при переключении документов в открытом окне. Кнопка **Обновить список** перечитывает
обе таблицы, сохраняя фильтры и выбранную скважину, если она ещё существует.
Сопоставление при сохранении по-прежнему читает актуальные данные из БД.
Чистые функции нормализации названий и классификации атрибутов используют
ограниченный LRU-кеш; правила сопоставления остаются прежними.
Пустое окно импорта не обращается к БД. Изменение не требует миграции.

Воспроизводимый замер: `python tests/performance/core_description_lookup_benchmark.py --wells 10000`.
На синтетической SQLite в памяти (10 000 скважин, 80 000 атрибутов, без
профилировщика) первый предпросмотр занял 3,74 с до изменений и 0,80 с после;
переключение документа — 3,41 с и 0,20 с. Число запросов: 23 → 2 для первого
предпросмотра, 23 → 0 при переключении. Это замер тестовых данных в окружении
разработки, а не гарантия времени на рабочей БД.

`check_duplicates` отдельно сообщает точный дубль документа по хешу и пересечения
его интервалов с ранее сохранёнными интервалами той же скважины. Наличие
пересечения само по себе не запрещает сохранение: решение остаётся за будущим
интерфейсом предпросмотра.

## Сохранение

```python
from core_description.database import save_core_import

result = save_core_import(
    session,
    parsed_document,
    well_id=selected_well_id,
    selected_interval_ids={"0:7", "0:8"},
    edits={"0:8": {"oil_saturation": "medium"}},
    duplicate_policy="reject",
    match_method="manual",
    match_confidence=1.0,
)
```

Устойчивый идентификатор строки имеет вид `"<индекс таблицы>:<индекс строки>"`.
Для внутреннего кода также принимается пара индексов. Сервис заново проверяет
скважину, непустое описание и конечные возрастающие глубины, сохраняет только
выбранные строки и фиксирует ручные правки. `duplicate_policy="reject"` является
безопасным режимом по умолчанию; `"replace"` явно заменяет документ и его дочерние
записи. Любая ошибка вызывает `rollback`, успешная операция — один `commit`.
