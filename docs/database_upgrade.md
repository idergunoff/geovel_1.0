# Обновление старой базы GeoVel

Код приложения и схема базы обновляются отдельно. Ошибка
`no such column: markup_reg.target_source_type` означает, что модель уже
использует новые поля, а в открытой SQLite-базе их ещё нет.
Эти поля добавляет миграция `b8c9d0e1f2a3`.

## Порядок обновления в Windows

1. Закройте GeoVel и программы, открывшие его базу данных.
2. Откройте терминал в папке проекта, где находятся `geovel.py`,
   `alembic.ini` и нужный `geovel_db.sqlite`. По умолчанию приложение и Alembic
   используют этот файл относительно рабочей папки. Если `sqlalchemy.url`
   в `alembic.ini` меняли, проверьте, что миграции обращаются к нужной базе.
3. Сделайте резервную копию базы. Команда ниже использует SQLite backup API
   и печатает имя отдельного файла с датой и временем:

   ```text
   venv\Scripts\python.exe -c "import sqlite3, datetime; from pathlib import Path; p=Path('geovel_db.sqlite').resolve(); s=sqlite3.connect(p.as_uri()+'?mode=ro', uri=True); b=p.with_name(p.stem+'.before_upgrade_'+datetime.datetime.now().strftime('%Y%m%d_%H%M%S_%f')+p.suffix); d=sqlite3.connect(str(b)); s.backup(d); d.close(); s.close(); print(b)"
   ```

4. Обновите файлы проекта, включая исправленные миграции, и выполните:

   ```text
   venv\Scripts\python.exe -m alembic current
   venv\Scripts\python.exe -m alembic upgrade head
   venv\Scripts\python.exe -m alembic current
   ```

   Последняя команда должна показать текущую вершину с отметкой `(head)`.
   В версии проекта с этим исправлением её идентификатор — `2f3a4b5c6d7e`.

5. После успешного обновления запустите приложение:

   ```text
   venv\Scripts\python.exe geovel.py
   ```

Здесь `venv` — имя существующего виртуального окружения. Если оно называется
`.venv`, замените начало пути. В Linux/macOS используйте `.venv/bin/python`.

## Почему миграция могла остановиться на `created_by`

При запуске `object.py` вызывает `Base.metadata.create_all(engine)`.
Этот вызов создаёт отсутствующие таблицы по текущим моделям, но не добавляет
новые столбцы в существующие таблицы и не обновляет версию Alembic.
Поэтому после запуска новой версии старая база может одновременно содержать:

- старую `markup_reg` без полей `target_source_*`;
- новую `well_log_cluster_dataset`, в которой уже есть `created_at`;
- новые таблицы кешей и словарей, ещё не отмеченные в истории Alembic.

Миграция `b1e2c3d4f5a6` раньше безусловно переименовывала `created_by` в
`created_at`, что вызывало `KeyError: 'created_by'` для уже новой таблицы.
Исправленная миграция проверяет фактическую схему. Следующие миграции также
учитывают уже существующие таблицы, поля, индексы и ограничения, сохраняя данные.
Повторный `upgrade head` продолжает обновление с записанной версии.

На компьютерах, где эти миграции уже выполнены, Alembic не запускает их
повторно: идентификаторы ревизий и цепочка зависимостей не меняются.
Если база уже находится на `head`, команда `upgrade head` оставляет её схему
и данные без изменений. Это поведение также проверяется тестами.

Не используйте `alembic stamp head` для исправления этой ошибки: команда
только меняет отметку версии, а отсутствующие поля не создаёт.
Если обновление остановится на ограничении `NOT NULL` или `UNIQUE`, сохраните
полный traceback: это требует проверки конкретных данных, а не пропуска миграции.

Исправление проверено на временных SQLite-базах со старой, новой и частично
обновлённой схемами. База с другого компьютера и запуск на Windows 8
этими тестами не проверяются.
